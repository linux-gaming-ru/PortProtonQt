# План headless-сервера PortProton и клиентских приложений

## Цель

Выделить библиотеку и запуск игр в headless core PortProton внутри общего
репозитория с PortProtonQt.
Headless-сервер, GUI и CLI разрабатываются в одном репозитории и виртуальном
окружении, но GUI и внешние приложения обращаются к core через один публичный
D-Bus API.

## Целевая схема

```text
┌──────────────────────┐  ┌──────────────────┐  ┌─────────────────────┐
│ PortProtonQt GUI     │  │ CLI              │  │ Внешний GUI         │
│ PySide6              │  │ Python           │  │ Vala / Rust / Electron│
└──────────┬───────────┘  └────────┬─────────┘  └──────────┬──────────┘
           └───────────────────────┼───────────────────────┘
                                   │ D-Bus session bus
                      ┌────────────▼─────────────┐
                      │ PortProton headless      │
                      │ Python server            │
                      │ library, config, launch, │
                      │ process lifecycle        │
                      └────────────┬─────────────┘
                                   │
                      Steam / GOG / EGS / PortProton
```

- Сервер запускается отдельным Python entry point без `QApplication`, окон,
  PySide6 и других GUI-импортов.
- Сервер — единственный владелец операций чтения и изменения библиотек,
  установки, запуска и остановки игр.
- GUI и CLI не читают внутренние файлы библиотек для получения игровых данных
  и не реализуют собственные пути запуска.
- Межпроцессный публичный транспорт — D-Bus session bus. HTTP-сервер на
  localhost не добавляется.
- `QLocalServer` временно остаётся внутренним механизмом одиночного экземпляра
  старого GUI; он не становится публичным API.

## Имена D-Bus

Предлагаемые значения, которые нужно зафиксировать перед первой реализацией:

| Назначение | Значение |
| --- | --- |
| Bus name | `ru.linux_gaming.PortProton1` |
| Object path | `/ru/linux_gaming/PortProton` |
| Interface | `ru.linux_gaming.PortProton1` |

Суффикс `1` — версия публичного интерфейса. Несовместимые изменения получают
новый интерфейс, а не меняют смысл существующих методов.

## Первый публичный API

Методы первой версии:

- `GetAPIVersion() -> u` — версия интерфейса.
- `GetCapabilities() -> as` — доступные источники и операции.
- `ListGames(a{sv} filters) -> aa{sv}` — игры с фильтрами по источнику,
  установке и тексту поиска.
- `GetGame(s game_id) -> a{sv}` — полная запись игры.
- `GetCover(s game_id) -> ay` — байты обложки, если она доступна.
- `InstallGame(s game_id, a{sv} options) -> s operation_id` — принять запрос на
  установку и вернуть его ID.
- `LaunchGame(s game_id, a{sv} options) -> s operation_id` — принять запрос на
  запуск и вернуть его ID.
- `CancelOperation(s operation_id) -> b` — отменить поддерживаемую операцию.
- `StopGame(s game_id) -> b` — остановить игру, если её можно остановить.
- `GetStatus() -> a{sv}` — состояние сервера и запущенных игр.

Первый серверный срез реализует `GetAPIVersion`, `GetCapabilities` и
`ListGames` для локальных PortProton `.desktop` ярлыков. Steam, GOG, EGS,
детали игры, запуск и управление операциями добавляются после фиксации
минимального межъязыкового контракта.

Текущая реализация этого среза устанавливается с `-Dgui=false`. Она требует
Python 3.11+ и `dbus-fast`, но не импортирует и не устанавливает PySide6, SDL3,
темы или GUI-модули. Возможность запуска игр не объявляется в capabilities до
переноса соответствующей логики в headless core.

Сигналы:

- `GamesChanged(s source)` — изменился список одного источника или всей
  библиотеки.
- `OperationChanged(s operation_id, s state, s message)` — изменилось состояние
  запуска или установки.
- `GameStarted(s game_id, u pid)` и `GameExited(s game_id, i exit_code)` —
  жизненный цикл игры.

Запись игры содержит стабильный ID, источник, отображаемое имя, состояние
установки и запуска, локальную обложку или её отсутствие, а также поддерживаемые
действия. ID имеют пространство источника: например, `steam:<appid>` и
`gog:<appid>`. Для локальных игр PortProton ID строится из нормализованного
пути/идентичности игры и не зависит от имени ярлыка.

D-Bus использует типизированные значения; методы не возвращают сериализованный
JSON. Ошибки выражаются стандартными D-Bus errors с документированными именами
для неверного ID, неустановленной игры, неподдерживаемого действия и внутренней
ошибки. Длинные операции не удерживают D-Bus вызов: метод быстро возвращает
`operation_id`, прогресс приходит сигналом.

## Владение данными и процессами

Сервер использует существующие данные PortProtonQt и не вводит вторую базу
игровой библиотеки. Он должен уметь перечислять игры из:

- локальных ярлыков PortProton;
- установленной библиотеки Steam;
- кэшированной библиотеки GOG;
- кэшированной библиотеки Epic Games Store.

Метаданные, уже закэшированные на диске, читаются локально. Сетевое обновление
метаданных остаётся отдельной операцией и не блокирует `ListGames`.

Сервер становится владельцем запущенных процессов и отслеживания их завершения.
Запуск использует существующие настройки PortProton и безопасные списки
аргументов (`shell=False`). GUI может закрыться, не завершая игру и не теряя
состояние операции.

Настройка пути PortProton не должна открывать диалог из серверного процесса.
Если путь не настроен, сервер возвращает код `NotConfigured`; GUI показывает
существующий экран выбора и сохраняет настройку через поддерживаемую операцию.

## CLI

CLI остаётся тонким D-Bus-клиентом. Команды CLI не обращаются к внутренним
файлам библиотек и не дублируют запуск. Сохраняются привычные флаги как
совместимые алиасы, где это возможно.

Предлагаемые действия:

- `portprotonqt games list [--json]`;
- `portprotonqt games get <id> [--json]`;
- `portprotonqt games launch <id>`;
- `portprotonqt games stop <id>`;
- `portprotonqt status [--json]`.

Для скриптов stdout содержит только результат, stderr — диагностику, код
завершения отличает успех от ошибки. `--list-games --json` считается текущим
прототипом: сейчас он перечисляет только PortProton `.desktop`-игры и при
переходе должен стать клиентом D-Bus API.

## Запуск сервера и упаковка

Сервер находится в репозитории PortProtonQt и устанавливается из того же
релиза отдельным entry point `portproton-server`. Один Meson-проект имеет два
режима: `gui=true` по умолчанию устанавливает существующий полный PPQT, а
`gui=false` устанавливает только headless core, сервер, CLI, PortProton-скрипты
и D-Bus-контракт. При разработке обычный `uv sync` по-прежнему создаёт GUI, CLI
и сервер рядом в одном venv.

План упаковки:

1. Добавить Meson option `gui` типа boolean со значением `true`. Полная сборка
   без новых параметров сохраняет текущий результат.
2. Разделить устанавливаемые Python-модули на headless и GUI. PySide6, SDL3,
   виджеты, темы, desktop entry и metainfo устанавливаются только при
   `gui=true`; серверные модули и PortProton-скрипты — в обоих режимах.
3. Разделить зависимости на headless и GUI: базовая часть содержит только
   зависимости core, а PySide6 и прочие GUI-зависимости устанавливаются для
   полного приложения. Обычный `uv sync` проекта устанавливает обе группы.
4. Устанавливать `portproton-server`, D-Bus introspection XML и activation
   service вместе с PPQT; дистрибутив при необходимости может вынести их в
   подпакет `portproton-core`.
5. Первый D-Bus вызов запускает сервер автоматически. Сервер работает, пока
   активны клиентские запросы или игровые процессы; политика выхода при
   простое фиксируется до релиза.
6. Для Flatpak GUI дать доступ только к well-known bus name PortProton, без
   полного доступа к session bus.

Сборка полного приложения остаётся прежней:

```sh
meson setup build
meson compile -C build
```

Headless-сборка использует тот же исходный проект:

```sh
meson setup build-headless -Dgui=false
meson compile -C build-headless
```

## Этапы реализации

### 0. Отдельный GTK4-клиент как проверка контракта

- Разместить небольшой Vala/GTK4-клиент в отдельном Git-репозитории вне
  репозитория PortProtonQt, с самостоятельной Meson-сборкой. Он не включается
  в основную сборку PortProtonQt и не требует Python-кода.
- Клиент показывает список игр через D-Bus и сообщение об ошибке, если сервер
  не запущен или API недоступен. Это проверяет межъязыковой контракт до
  переноса основного GUI.
- GTK-клиент остаётся отдельным проектом и может подключать общий репозиторий как Meson
  subproject с `default_options: ['gui=false']`. В его build-граф попадает
  только headless-режим; Qt GUI не собирается и не устанавливается.
- Для встраивания использовать D-Bus как границу процесса и данных. Клиентское
  приложение может встроить собственное представление в GTK/Qt/Web UI, но не
  виджет из отдельного процесса; при необходимости встраиваемого виджета его
  реализуют внутри соответствующего GUI-клиента.

**Готово, когда:** Vala-клиент собирается отдельно и читает игры по
документированному D-Bus API.

Пример подключения из Vala-проекта:

```meson
subproject('portprotonqt', default_options: ['gui=false'])
```

Для воспроизводимой сборки клиент фиксирует конкретную ревизию PPQT в
`subprojects/portprotonqt.wrap`. Системный пакет может собирать тот же исходник
дважды с разными install tags: `headless` и `gui`, не создавая второй проект.

### 1. Зафиксировать и описать контракт

- Утвердить имена D-Bus и сигнатуры методов.
- Утвердить поля записи игры, ID, коды ошибок и сигналы.
- Добавить introspection и примеры вызовов для клиента.

**Готово, когда:** простой клиент на любом языке может получить версию API и
список игр по документированным сигнатурам.

### 2. Выделить headless core

- Найти Qt-зависимые импорты в конфигурации, библиотеках и запуске.
- Перенести только нужную бизнес-логику в модули, импортируемые без PySide6.
- Сохранить один репозиторий, один формат данных и обычный `uv sync` для полной
  среды разработки.
- Зафиксировать минимальный набор runtime-зависимостей headless entry point.

**Готово, когда:** импорт и запуск `portproton-server` не требуют PySide6,
дисплея или `QApplication`, а полный PPQT по-прежнему запускается из того же
venv.

### 3. Реализовать headless-сервер

- Экспортировать интерфейс на пользовательской session bus.
- Реализовать список игр всех поддерживаемых источников, детали, обложки,
  установку, запуск, остановку и состояние.
- Сохранить владение работниками и игровыми процессами до завершения.
- Проверять входные ID и параметры на границе D-Bus.

**Готово, когда:** сервер запускается отдельно и работает без GUI, а вызовы
возвращают данные и состояние операций.

### 4. Перевести основной GUI на роль клиента

- Заменить прямое чтение игровых библиотек на D-Bus методы и сигналы.
- Сохранить текущие действия и отображение GUI.
- Удалить из GUI только те участки бизнес-логики, которые теперь принадлежат
  серверу.
- Оставить `QLocalServer` только для старого single-instance forwarding до
  завершения миграции.

**Готово, когда:** GUI показывает те же игры и вызывает запуск через сервер.

### 5. Перевести CLI на D-Bus

- Реализовать команды списка, деталей, запуска, остановки и статуса как клиента.
- Сохранить совместимые старые флаги и форматировать JSON на границе CLI.
- Удалить прямую логику чтения desktop-файлов из CLI после переключения.

**Готово, когда:** GUI и CLI используют один сервер и возвращают согласованное
состояние.

### 6. Упаковать и проверить межъязыковой доступ

- Установить activation service для пакетного и Flatpak вариантов.
- Проверить разрешения session bus без широкого доступа.
- Добавить минимальные примеры клиента на Vala, Rust и JavaScript/Electron либо
  один универсальный D-Bus introspection-пример плюс короткие клиенты.
- Добавить проверки API-контракта, запуска службы, закрытия процессов и
  совместимости старого single-instance пути.

**Готово, когда:** стороннее GUI может получить библиотеку, запустить и
остановить игру и получать события без импорта Python-кода PortProtonQt.

## Не входит в первую версию

- HTTP/REST на localhost.
- Удалённый доступ по сети или system bus.
- Перенос всей установки, загрузки, настроек и системного управления в API до
  появления конкретных клиентских сценариев.
- Удаление `QLocalServer` до завершения GUI-миграции.

## Главные риски и проверки

- Некоторые существующие методы запуска зависят от GUI и требуют выделения
  общего сервиса.
- Вызовы D-Bus не должны блокировать главный цикл GUI или задерживать ответы
  сервера на сетевой работе.
- API должен отличать игру, которой нет, игру без установки и игру, которую
  нельзя запустить.
- Обложки могут отсутствовать; пустое значение должно быть штатным ответом.
- Сервис не должен оставлять дочерние процессы без владельца после завершения
  сервера.
- Изменения публичных сигнатур требуют новой версии интерфейса или
  совместимого расширения.
